# README 视觉设计规范

> 面向本仓库所有会话与贡献者。**改 README、换截图、做配图之前先读本文件。**
> 目标：README 是产品主页，首屏讲清「这是什么 + 怎么装」，亮点交给统一卡片，细节交给文档与 Wiki。
> 2.8.0 修订：按用户反馈把安装指引提前；功能卡改成同尺寸图片，不再靠图片高度硬撑。

## 1. 风格

- GitHub 原生主题：正文颜色交给 GitHub，Light / Dark 都成立，不用内联 CSS 改页面底色。
- 强调色只出现在图片里：背景 `#0A0A16`，紫 `#8B5CF6`，蓝 `#536DFE`。
- 字体、字号、行距不手写：用 Markdown 语义层级，`**粗体**` 做卡片标题。
- 不用「唯一」「最强」「首创」这类自我评价；标题用「有趣的功能」这类中性说法。

## 2. 页面结构（顺序固定）

1. **Hero**：`assets/hero-banner.jpg`，1920×640，JPEG q92。左侧品牌与一句话价值，右侧真实界面拼贴与四个环节（发现好片 → 沉浸观看 → 记录精彩 → 轻松重逢）。新版本成图由绘图流程交付，README 只替换文件，不改布局。
2. **Badges**：Releases / HarmonyOS / ArkTS / mpv / Python / License，六个以内。
3. **一句话定位**：产品主标题、副标题、产品标签、本版短条、截图声明。版本短条只写用户可感知的变化，不写内部修复细节。
4. **快速开始**（2.8.0 起提前）：三步编号段落 + 「以后怎么更新」。用户不用滚过功能展示才找到安装入口。
5. **有趣的功能**：标题下直接进 ①，不铺垫。**一条能力一块，图在上、标题与一句说明紧跟在下**。
   - 编号按当前展示顺序连续排；版本更新时新点可以往前排、旧点可以并成短句，但编号不能跳。
   - 功能卡图片统一 **720×440**、`width="100%"`，两张一行；卡片标题与说明左对齐，图也左对齐。
   - **禁止 `align="center"`**：图一旦居中，就和下面左对齐的文字错开，读者分不清说明属于哪张图。
   - 没合格截图的能力不造假图，在末行用 `<sub>` 或 `>` 引用块写清楚，编号照排。
   - 一张图只配一条说明；同一能力需要第二张图时另起一块。
6. **完善的基础功能**：两行各四张小卡，统一 **360×240**、`width="100%"`；每张只给一个短语（≤ 10 字）。不便配图的能力在卡片下面补一行纯词列表。
7. **播放链路**：`assets/architecture.png` + 4–6 条短句收进 GitHub 原生 `<details>`；外挂字幕留在折叠外。
8. **文档**：Wiki 在前；仓库内文档按「第一次装 / 已有旧版 / 使用与排错 / 维护与贡献」分行。
9. **交流**：讨论群、更新频道。
10. **许可**：MIT + 非官方声明。

## 3. 图片策略

**不使用抽象占位海报或 AI 生成的假 UI。** 界面截图必须来自真实运行的程序。

| 画面内容 | 处理方式 |
|---|---|
| 演员列表、演员详情、头像、演员名与资料 | **真实截图**，不打码 |
| 封面 / 海报、横幅、剧照、系列与分类缩略图 | **真实截图 + 打码**（像素化马赛克，长边约 26 格） |
| 数字、番号、标记、标题、标签等 UI 文字 | 保留真实值 |

做法：客户端连真实媒体库，所有图片请求走本地像素化代理（除演员头像外统一缩到极小再放大回去），截图后不逐张手画遮挡。

生成 Hero 与拼贴图时，只允许拼接真实截图 + 真实 App 图标；README 功能卡可以从真实截图裁切、等比缩放、补深色边，**不能改造截图里的 UI**。

2.8.0 取图规则：六 Tab 顶栏、甄选抽屉、抽卡、演员、收藏用 `v280-*.png`；亮点、出演年龄、番号前缀、统计、座次、俗称搜索、刷一刷、首页范围、备份仍用各能力最清楚的旧截图。统一卡片由 `_publish/.local/prepare_280_readme_images.py` 生成，脚本只做裁切与缩放。

## 5. 文案约束

**要的口语，不要功能说明书。** 一条 = 钩子 → 亮点 → 收益，2–4 句、60–110 字。

- 钩子可以是痛点或问句；收尾给收益，允许「再也不用…」这种口气。
- 具体到这个库里的动作：说「点哪张从哪秒开始播」，不说「支持按时间点定位播放」。
- 三段式：痛点 → 一句关键动作 → 优化词并列（`离散人数多选 · 导演可包含可排除`）。优化词不逐条解释。
- 直接描述 UI 长什么样是废话；功能覆盖范围写成气势，不写成清单。
- 允许的对照：只描述可核实的观感差异，不编造对方没有的能力。

禁止：AI 腔（「不是……而是……」「本质上」「值得一提的是」「这就意味着」）、解释功能之间的等价关系、散点罗列、「仅支持」「暂时没有」「唯一」「最强」、每条都同一句式开头。

> 准确但没人想读不是合格文案。用户要的是带情绪的表达，不是压缩过的规格表。

## 6. 实现约束

- 只用 GitHub 原生 Markdown / HTML：`<p>`、`<table>`、`<img width>`、`<details>`；不要外部 CSS / JS。
- 表格只排截图与短卡片，不承载长正文。功能卡两列、基础卡四列；窄屏不能横向滚动。
- 功能卡与基础卡都走 `width="100%"`，由图片本身的统一比例保证等高；不再单独给 `<img>` 写 `height`。
- 正文文字不进图片（Hero 标题除外），否则 Light / Dark 主题下会失衡。
- 不夸大功能：文案只描述代码里真实存在的行为；新能力先合代码再上图。

## 7. 验收

- 首屏不滚动就能看懂：这是 HarmonyOS 原生 Amane 客户端，以及两三项最核心的价值；安装入口在功能展示之前。
- 每张截图都紧接对应说明；没有「图里有、文中无」的功能暗示，也没有说明离图太远。
- 功能区两张一行、基础区四张一行，卡片等高；没有 `align="center"`。
- 封面全部已打码，演员头像清晰；没有真实地址、token 或凭据入镜。
- GitHub Light / Dark、桌面 / 手机宽度下均无溢出。
