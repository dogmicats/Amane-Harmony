# README 视觉设计规范

> 面向本仓库所有会话与贡献者。**改 README、换截图、做配图之前先读本文件。**
> 目标：README 是产品主页，第一屏讲清「这是什么 + 几个亮点」，其余交给截图和 Wiki。

## 1. 风格

- GitHub 原生主题：正文颜色一律交给 GitHub（Light / Dark 都成立），**不要**用内联 CSS 改页面底色。
- 强调色只出现在图片里：背景 `#0A0A16`，紫 `#8B5CF6`，蓝 `#536DFE`。
- 字体、字号、行距不手写——用 Markdown 语义层级（`##` 一级分区，`**粗体**` 做卡片标题）。

## 2. 页面结构（顺序固定）

1. **Hero**：`assets/hero-banner.png`，1600×650，左侧品牌与一句话价值，右侧三张真实界面。
2. **Badges**：Releases / HarmonyOS / ArkTS / mpv / Python / License，六个以内。
3. **一句话定位 + 截图声明**：客户端做什么、旁挂服务补什么；紧跟一行「截图取自作者自建库，封面、横幅与剧照已打码」。
4. **有趣的功能**（2026-11-11 起取代 2.4.0 时期的旧称）：**编号连续**，标题下直接进 ①，不要铺垫段落。
   版式按图片比例分三层，**一条能力一块，图片和它的说明永远上下相邻**：
   - **卡片行**：比例接近的整屏图（720×1507 一类）放同一行，一行三列，图 210 宽、
     `align="center"`，标题与一句说明在图正下方；
   - **文字行**：没图、或截图里有测试数据的（④ 亮点 / ⑤ 就地起播 / ⑥ 弹幕）并成一行三格，
     一条一句，不占大块高度；
   - **宽幅图**：最该展示的一条用 `width="100%"` 独占一行（当前是 ⑧ 出演年龄），
     其余比例偏方的功能图居中、460 宽，说明紧跟图下方。
   **禁止「左图右文」并排**（2026-11-11 用户驳回）：竖屏截图 720×1507 缩到 150 宽仍有 314 高，
   右侧只有两三行字，行高被图撑起来，文字下方空出一大片，第一眼就是「这页没排版」。
   要并排只能图高 ≈ 文高，本仓库的截图比例差太远（0.55–2.17 都有），一律改上下结构。
   **版本更新时重新判断展示价值、重拍并重新分配图位**：新点可以拿到宽幅主推位，旧点可以降为短句或
   让出图位；但**编号顺序不变**，能力仍续在末尾，不要为了「保住原来那张图」把新能力一直写成文字。
   同一机制只占一个名额（抽卡与演员页「盲盒」是同一个随机剧照墙，合并为一条；盲盒不再单独占图位）。
5. **完善的基础功能**（2026-11-11 起取代 2.4.0 时期的旧称）：两行各四张小图
   （首页 / 媒体库 / 演员 / 详情 / 剧照 / 筛选 / 搜索 / 播放器设置），每张只给一个短语（≤ 10 字），不写解释句；
   不便配图的能力在卡片下面补一行**纯词列表**，只列词、不解释。本次更新换过版式的页面用新截图，别留旧图。
6. **播放链路**：`assets/architecture.png` + 4–6 条短句（块缓存、并行预取、硬解、玻璃控制层、参数锁定、外挂字幕）。
7. **快速开始**：三步表格（部署服务 / 安装客户端 / 连接媒体库），细节链去 `docs/`。
8. **文档**：Wiki 在前，仓库内文档一列排完。
9. **许可**：MIT + 非官方声明。

> 不写「唯一」「最强」这类自我评价，也不要把功能写成「因为库不一样所以只能自己做」的苦衷；
> 标题用「有趣的功能」这类中性说法，不做排他性宣称。确需对照时最多一句，且要能对上
> Emby / Jellyfin 生态的实际能力（对比依据见 PR 说明与 wiki）。

## 3. 图片策略（2026-11-10 起）

**不再使用抽象占位海报或 AI 生成的假 UI。** 界面截图必须来自真实运行的程序。

| 画面内容 | 处理方式 |
|---|---|
| 演员列表、演员详情、头像、演员名与资料 | **真实截图**，不打码 |
| 封面 / 海报、横幅、剧照、系列与分类缩略图 | **真实截图 + 打码**（像素化马赛克，长边约 26 格） |
| 数字、番号、标记、标题、标签等 UI 文字 | 保留真实值 |

做法：客户端连真实媒体库，所有图片请求走一个本地像素化代理（除演员头像外的图片统一缩到极小再放大回去），代理之后的截图不需要再后期修图；**不要**逐张手画矩形遮挡，容易漏、也对不上圆角。

生成 Hero 与配图时，只允许拼接真实截图 + 真实 App 图标，禁止用 AI 生成界面。

## 5. 文案约束（2026-11-10 加，用户明确要求）

- **一句说完**：亮点条目最多两行，完善的基础功能只给短语。写不下就说明该拆到 Wiki。
- **先说功能，不先说处境**：不要写「通用客户端面向电影剧集，我们的库不是那样组织的，所以只能自己做」——
  这是把亮点写成苦衷。直接写「① 共演检索：最多 6 位演员同台，人数离散多选，导演可只看或排除」。
- **对照最多一句**：整个 README 里「别处没有」这类对照只出现一次（放在最有说服力的那条下面），
  且必须是可核对的事实（例：Jellyfin 的 trickplay 只作用于进度条拖动、需库级预生成）。
- **不写自我评价**：不用「唯一」「最强」「业界首创」。也不用「仅支持」「暂时没有」这类自曝短板的话。
- **不重复句式**：编号条目不要都用同一个句式开头。

## 6. 实现约束

- 只用 GitHub 原生 Markdown / HTML：`<p align="center">`、`<table>`、`<img width>`、`<details>`。不要外部 CSS / JS。
- 表格只用来排截图与短卡片，**不要**用表格承载长正文。
- 手机截图一行 3–4 张；不要一屏塞 6 张。窄屏下不能出现横向滚动。
- 正文文字不进图片（Hero 的标题除外），否则 Light / Dark 主题下会失衡。
- 不夸大功能：文案只描述代码里真实存在的行为，新增能力先合代码再上图。

## 7. 验收

- 首屏不滚动就能看懂：这是 HarmonyOS 原生 Amane 客户端，以及两三项最核心的价值。
- 每张截图都能对应到 README 里的一句话；没有「图里有、文中无」的功能暗示。
- 封面全部已打码，演员头像清晰；没有任何真实地址、token 或凭据入镜。
- GitHub Light / Dark、桌面 / 手机宽度下均无溢出。
